<Intro>
  <p>O que funciona em dev costuma quebrar em produção. Este checklist cobre os pontos essenciais: limites de recursos, health checks, desligamento gracioso e alta disponibilidade.</p>
</Intro>

<table class="example-table">
  <tbody>
    <FileHeader filename="1-recursos.yaml" />
    <Row>
      <p slot="docs"><strong>Defina requests e limits de recursos.</strong> Sem requests, o scheduler não tem informação suficiente para tomar boas decisões e seu Pod pode acabar em um node já sobrecarregado. Sem limits, um vazamento de memória pode derrubar o node inteiro.</p>
      <Fragment slot="code">
```yaml
resources:
  requests:
    cpu: 100m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 256Mi
```
      </Fragment>
    </Row>
    <Row last>
      <p slot="docs"><strong>Iguale o limit de memória ao request.</strong> Isso coloca o Pod na classe QoS Guaranteed, tornando o scheduling mais previsível. Para CPU, tudo bem ter um limit maior que o request (permitindo burst), mas memória deve ser igual para evitar OOMKills inesperados.</p>
      <Fragment slot="code">
```yaml
resources:
  requests:
    cpu: 100m
    memory: 512Mi
  limits:
    cpu: 1
    memory: 512Mi
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="2-probes.yaml" />
    <Row>
      <p slot="docs"><strong>Configure o readiness probe.</strong> Sem ele, o tráfego começa a chegar nos Pods antes que eles estejam prontos. Durante rolling updates, os usuários acabam vendo erros. O probe deve verificar se a aplicação realmente consegue atender requisições, não apenas se o processo está rodando.</p>
      <Fragment slot="code">
```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 5
  failureThreshold: 3
```
      </Fragment>
    </Row>
    <Row last>
      <p slot="docs"><strong>Configure o liveness probe.</strong> Ele reinicia processos que travaram. Mas cuidado: se o check for muito agressivo, você vai reiniciar Pods saudáveis que estão apenas sob carga alta. Mantenha-o mais simples que o readiness — basta verificar se o processo responde.</p>
      <Fragment slot="code">
```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 10
  failureThreshold: 3
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="3-shutdown.yaml" />
    <Row>
      <p slot="docs"><strong>Trate o sinal SIGTERM.</strong> O Kubernetes envia SIGTERM, aguarda o tempo definido em <code>terminationGracePeriodSeconds</code> e depois envia SIGKILL. Sua aplicação precisa capturar o SIGTERM e finalizar as requisições em andamento. O padrão de 30 segundos muitas vezes não é suficiente para operações mais longas.</p>
      <Fragment slot="code">
```yaml
spec:
  terminationGracePeriodSeconds: 60
  containers:
    - name: api
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 5"]
```
      </Fragment>
    </Row>
    <Row last>
      <p slot="docs"><strong>O truque do sleep no preStop:</strong> Load balancers levam alguns segundos para remover os endpoints da lista. Sem esse delay, requisições ainda chegam em Pods que já estão terminando. O sleep dá tempo para o LB se atualizar, e só então sua aplicação processa o SIGTERM de forma limpa.</p>
      <Fragment slot="code">
```javascript
process.on('SIGTERM', async () => {
  console.log('SIGTERM recebido, finalizando requisições...');
  server.close(async () => {
    await db.disconnect();
    process.exit(0);
  });
});
```
      </Fragment>
    </Row>
  </tbody>
</table>

    <FileHeader filename="4-replicas.yaml" />
    <Row last>
      <p slot="docs"><strong>Rode múltiplas réplicas.</strong> Uma única réplica é um ponto único de falha. Durante manutenção de nodes, deploys ou crashes, seu serviço fica indisponível. Use no mínimo 2 réplicas para qualquer serviço importante, e 3 ou mais para os fluxos críticos.</p>
      <Fragment slot="code">
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
```
      </Fragment>
    </Row>
  </tbody>
</table>

  <tbody>
    <FileHeader filename="5-anti-affinity.yaml" />
    <Row last>
      <p slot="docs"><strong>Distribua os Pods entre nodes diferentes.</strong> Ter 3 réplicas no mesmo node ainda é um ponto único de falha. O anti-affinity garante que os Pods fiquem em nodes separados. Use <code>preferredDuringScheduling</code> para que o agendamento ainda funcione quando houver poucos nodes disponíveis.</p>
      <Fragment slot="code">
```yaml
spec:
  template:
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels:
                    app: api
                topologyKey: kubernetes.io/hostname
```
      </Fragment>
    </Row>
  </tbody>
</table>

    <FileHeader filename="6-pdb.yaml" />
    <Row last>
      <p slot="docs"><strong>Defina um Pod Disruption Budget.</strong> Sem PDB, um <code>kubectl drain</code> pode remover todos os seus Pods de uma vez durante uma manutenção. O PDB garante uma disponibilidade mínima. Com <code>maxUnavailable: 1</code>, apenas 1 Pod pode ficar indisponível por vez.</p>
      <Fragment slot="code">
```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: api
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="7-seguranca.yaml" />
    <Row>
      <p slot="docs"><strong>Remova privilégios de root.</strong> Rodar como root dentro do container é desnecessário para a maioria das aplicações — e perigoso caso o container seja comprometido. Configure <code>runAsNonRoot: true</code> e especifique um user ID.</p>
      <Fragment slot="code">
```yaml
spec:
  template:
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 1000
```
      </Fragment>
    </Row>
    <Row last>
      <p slot="docs"><strong>Use filesystem read-only.</strong> Isso impede que atacantes instalem malware no container. Para diretórios que precisam de escrita (como tmp ou cache), use volumes <code>emptyDir</code>. Aproveite e remova todas as capabilities que sua aplicação não precisa.</p>
      <Fragment slot="code">
```yaml
      containers:
        - name: api
          securityContext:
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir: {}
```
      </Fragment>
    </Row>
  </tbody>
</table>

    <FileHeader filename="8-rolling-update.yaml" />
    <Row last>
      <p slot="docs"><strong>Configure a estratégia de rolling update.</strong> Os valores padrão são bem conservadores. O <code>maxSurge</code> define quantos Pods extras podem existir durante o update (controla a velocidade). O <code>maxUnavailable</code> define quantos podem ficar fora (controla a capacidade). Para zero downtime, use <code>maxUnavailable: 0</code>.</p>
      <Fragment slot="code">
```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
```
      </Fragment>
    </Row>
  </tbody>
</table>

    <FileHeader filename="9-labels.yaml" />
    <Row last>
      <p slot="docs"><strong>Adicione labels operacionais.</strong> Você vai precisar delas quando tudo estiver pegando fogo às 3 da manhã. Use <code>app</code> para selecionar recursos, <code>version</code> para decidir rollbacks, e <code>team</code> para identificar quem é responsável.</p>
      <Fragment slot="code">
```yaml
metadata:
  name: api
  labels:
    app: api
    app.kubernetes.io/name: api
    app.kubernetes.io/version: "2.1.0"
    app.kubernetes.io/component: backend
    team: platform
    environment: production
```
      </Fragment>
    </Row>
  </tbody>

    <FileHeader filename="10-completo.yaml" />
    <Row last>
      <p slot="docs"><strong>Deployment completo pronto para produção.</strong> Aqui está tudo junto. Este Deployment sobrevive a falhas de node, faz deploy de forma segura, desliga graciosamente e não roda como root.</p>
      <Fragment slot="code">
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  labels:
    app: api
    team: platform
spec:
  replicas: 3
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      terminationGracePeriodSeconds: 60
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels:
                    app: api
                topologyKey: kubernetes.io/hostname
      containers:
        - name: api
          image: api:2.1.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 256Mi
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 10
          securityContext:
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 5"]
```
      </Fragment>
    </Row>
