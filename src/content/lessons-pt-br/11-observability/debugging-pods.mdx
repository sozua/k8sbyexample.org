<Intro>
  <p>Quando um Pod falha, siga este checklist: verifique o status, leia os eventos, inspecione os logs e depois entre no container. A maioria dos problemas se encaixa em três categorias: problemas com a imagem, falhas na aplicação ou falta de recursos.</p>
</Intro>

<table class="example-table">

    <TerminalHeader cmd="kubectl get pods -o wide" />
    <Row last terminal>
      <p slot="docs">Comece por aqui. O status já indica onde procurar. <code>ImagePullBackOff</code> = problema com a imagem. <code>CrashLoopBackOff</code> = a aplicação inicia mas quebra logo em seguida. <code>Pending</code> = problema de scheduling. <code>Running</code> mas não ready = algum probe está falhando.</p>
      <Fragment slot="code">
```bash
$ kubectl get pods -o wide
NAME        READY   STATUS             RESTARTS   AGE   NODE
api-6f7d8   0/1     ImagePullBackOff   0          2m    worker-1
db-8k2x9    0/1     CrashLoopBackOff   5          10m   worker-2
web-3n4m5   0/1     Pending            0          5m    <none>
cache-9z8y  1/1     Running            0          1h    worker-1
```
      </Fragment>
    </Row>
  </tbody>
</table>

      <p slot="docs">A seção Events no final do output é sua melhor amiga. Ela mostra a sequência exata do que aconteceu. No caso de <code>ImagePullBackOff</code>, você verá o erro específico — tag errada, falha de autenticação no registry privado ou problemas de rede.</p>

    <TerminalHeader cmd="kubectl describe pod web-3n4m5" />
    <Row last terminal>
      <p slot="docs"><code>Pending</code> significa que o scheduler não conseguiu alocar o Pod em nenhum node. Verifique os eventos para entender o motivo: CPU ou memória insuficiente, nenhum node atende às regras de affinity, ou todos os nodes têm taints que o Pod não tolera. Note que a coluna <code>NODE</code> mostra <code>&lt;none&gt;</code>.</p>
      <Fragment slot="code">
```bash
$ kubectl describe pod web-3n4m5 | tail -10
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  5m    default-scheduler  0/3 nodes are available:
           1 Insufficient cpu, 2 node(s) had taint
           {node-role.kubernetes.io/master: }, that the pod didn't tolerate.

$ kubectl describe nodes | grep -A5 "Allocated resources"
```
      </Fragment>
    </Row>
  </tbody>

    <TerminalHeader cmd="kubectl run debug --rm -it --image=nicolaka/netshoot -- bash" />
    <Row last terminal>
      <p slot="docs">Para debug de rede, você precisa de ferramentas que a maioria das imagens não tem. A imagem <code>netshoot</code> vem com curl, dig, nmap, tcpdump e muito mais. Perfeita para testar conectividade de Services, DNS e network policies.</p>
      <Fragment slot="code">
```bash
$ kubectl run debug --rm -it --image=nicolaka/netshoot -- bash

bash-5.1$ dig +short api-service.default.svc.cluster.local
10.100.45.23

bash-5.1$ nc -zv api-service 8080
Connection to api-service 8080 port [tcp/*] succeeded!

bash-5.1$ curl -v http://api-service:8080/health

bash-5.1$ mtr --report api-service

bash-5.1$ tcpdump -i eth0 port 8080 -w /tmp/capture.pcap
```

    <TerminalHeader cmd="kubectl get events --sort-by='.lastTimestamp'" />
    <Row last terminal>
      <p slot="docs">Uma visão geral de tudo que está acontecendo no cluster. Os eventos desaparecem após 1 hora por padrão. Você pode filtrar por namespace, tipo ou objeto específico. Os Warnings costumam ser os mais interessantes.</p>
      <Fragment slot="code">
```bash
$ kubectl get events --sort-by='.lastTimestamp' | tail -20

$ kubectl get events --field-selector type=Warning

$ kubectl get events --field-selector involvedObject.name=api-6f7d8

$ kubectl get events -w
0s    Warning   FailedMount   pod/api-6f7d8   MountVolume.SetUp failed
0s    Normal    Pulled        pod/db-8k2x9    Container image pulled
```

    </Row>

    <TerminalHeader cmd="kubectl top pods --sort-by=memory" />
    <Row last terminal>
      <p slot="docs">Problemas de recursos causam OOMKills e throttling de CPU. O comando <code>top</code> mostra o consumo real (requer o metrics-server instalado). Compare os valores com os limits configurados. Um número alto de restarts geralmente indica que o Pod está sendo OOMKilled.</p>
      <Fragment slot="code">
```bash
$ kubectl top pods --sort-by=memory
NAME        CPU(cores)   MEMORY(bytes)
api-6f7d8   250m         512Mi
db-8k2x9    100m         1024Mi
web-3n4m5   50m          128Mi

$ kubectl get pod db-8k2x9 -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'
OOMKilled

$ kubectl describe pod api-6f7d8 | grep -A2 Limits
    Limits:
      cpu:     500m
      memory:  256Mi
```

    <TerminalHeader cmd="kubectl port-forward pod/db-8k2x9 5432:5432" />
    <Row last terminal>
      <p slot="docs">Precisa conectar diretamente a um Pod? O port-forward cria um túnel a partir do seu localhost. Muito útil para acessar bancos de dados, testar endpoints ou conectar debuggers. O túnel fica aberto até você pressionar Ctrl+C.</p>
      <Fragment slot="code">
```bash
$ kubectl port-forward pod/db-8k2x9 5432:5432 &
Forwarding from 127.0.0.1:5432 -> 5432

$ psql -h localhost -p 5432 -U admin mydb

$ kubectl port-forward svc/api-service 8080:80

$ kubectl port-forward pod/api-6f7d8 8080:80 9090:9090
```
