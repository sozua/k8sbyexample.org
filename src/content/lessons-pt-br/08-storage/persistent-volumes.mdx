<Intro>
  <p>PersistentVolumes (PVs) são recursos de storage cluster-wide provisionados por admins ou dinamicamente. Eles abstraem o storage subjacente (discos cloud, NFS, local). Pods reclamam storage via PersistentVolumeClaims sem conhecer detalhes.</p>
</Intro>

<table class="example-table">
  <tbody>
    <FileHeader filename="pv.yaml" />
    <Row last>
      <p slot="docs">PV define uma peça de storage no cluster. <code>capacity</code> especifica tamanho. <code>accessModes</code> controla como pode ser montado. <code>persistentVolumeReclaimPolicy</code> controla limpeza.</p>
      <Fragment slot="code">
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-data
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: standard
  hostPath:
    path: /data/pv-data
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="pv-access-modes.yaml" />
    <Row last>
      <p slot="docs">Access modes definem como volumes podem ser montados. RWO (ReadWriteOnce): único node leitura-escrita. ROX (ReadOnlyMany): múltiplos nodes somente leitura. RWX (ReadWriteMany): múltiplos nodes leitura-escrita. RWOP (ReadWriteOncePod, 1.22+): único Pod apenas. AWS EBS/Azure Disk: apenas RWO. NFS: RWO, ROX, RWX.</p>
      <Fragment slot="code">
```yaml
spec:
  accessModes:
    - ReadWriteOnce
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="pv-reclaim.yaml" />
    <Row last>
      <p slot="docs">Políticas de reclaim controlam o que acontece quando um PVC é deletado. <code>Retain</code>: PV permanece, dados preservados, limpeza manual necessária. <code>Delete</code>: PV e storage subjacente deletados automaticamente. Após deleção do PVC com Retain, status do PV muda para "Released". Admin deve deletar PV ou remover claimRef para reusar.</p>
      <Fragment slot="code">
```yaml
spec:
  persistentVolumeReclaimPolicy: Retain
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="pv-cloud.yaml" />
    <Row>
      <p slot="docs">Volume AWS EBS: referencia um volume EBS existente pelo ID. Volumes EBS são apenas RWO e devem estar na mesma AZ que o node. Para produção, use provisionamento dinâmico via StorageClass.</p>
      <Fragment slot="code">
```yaml
spec:
  capacity:
    storage: 100Gi
  accessModes: [ReadWriteOnce]
  awsElasticBlockStore:
    volumeID: vol-0123456789abcdef0
    fsType: ext4
```
      </Fragment>
    </Row>
    <Row>
      <p slot="docs">GCE Persistent Disk: referencia um disco GCE pelo nome. Similar ao EBS, PDs são zonais e RWO.</p>
      <Fragment slot="code">
```yaml
spec:
  gcePersistentDisk:
    pdName: my-disk
    fsType: ext4
```
      </Fragment>
    </Row>
    <Row last>
      <p slot="docs">Volume NFS: monta um filesystem de rede. Suporta RWX (múltiplos nodes leitura-escrita), sendo adequado para storage compartilhado.</p>
      <Fragment slot="code">
```yaml
spec:
  nfs:
    server: nfs-server.example.com
    path: /exports/data
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">

    <FileHeader filename="pv-local.yaml" />
    <Row last>
      <p slot="docs">Node affinity restringe quais nodes podem acessar o PV. Necessário para volumes locais e alguns tipos de storage. O PV só pode ser usado por Pods agendados em nodes correspondentes.</p>
      <Fragment slot="code">
```yaml
spec:
  capacity:
    storage: 100Gi
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Delete
  storageClassName: local-storage
  local:
    path: /mnt/disks/ssd1
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values:
                - node-1
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="pv-block.yaml" />
    <Row>
      <p slot="docs"><code>volumeMode: Filesystem</code> (padrão) monta o PV como diretório. O storage é formatado com um filesystem (ext4, xfs) e montado no container.</p>
      <Fragment slot="code">
```yaml
spec:
  volumeMode: Filesystem
  capacity:
    storage: 10Gi
```
      </Fragment>
    </Row>
    <Row last>
      <p slot="docs"><code>volumeMode: Block</code> expõe dispositivo de bloco raw sem filesystem. Use <code>volumeDevices</code> (não volumeMounts) no spec do Pod. Modo Block é para bancos de dados que gerenciam seu próprio formato de storage.</p>
      <Fragment slot="code">
```yaml
spec:
  containers:
    - name: app
      volumeDevices:
        - name: data
          devicePath: /dev/xvda
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: block-pvc
```
      </Fragment>
    </Row>
  </tbody>
</table>

    <Row last terminal>
      <p slot="docs">Debug problemas de PV verificando status e eventos. Problemas comuns: access mode errado, mismatch de capacidade, mismatch de storage class, node affinity prevenindo binding.</p>
      <Fragment slot="code">
```bash
$ kubectl get pv
NAME      CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS
pv-data   10Gi       RWO            Retain           Available
pv-db     50Gi       RWO            Delete           Bound

$ kubectl describe pv pv-data

$ kubectl patch pv pv-data -p '{"spec":{"claimRef":null}}'
persistentvolume/pv-data patched

$ kubectl get pv pv-data -o yaml | grep -A10 status
status:
  phase: Available

$ kubectl get pvc --all-namespaces | grep Pending
default   db-data   Pending   <none>

$ kubectl get storageclass
NAME                 PROVISIONER
standard (default)   ebs.csi.aws.com
```
