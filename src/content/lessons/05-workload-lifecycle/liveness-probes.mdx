<Intro>
  <p>Liveness probes detect broken containers. If the probe fails consecutively (failureThreshold times), Kubernetes kills and restarts the container. Use for: deadlocks, memory leaks, unrecoverable errors.</p>
</Intro>

<table class="example-table">
  <tbody>
    <FileHeader filename="pod-liveness.yaml" />
    <Row last>
      <p slot="docs">HTTP probe is the most common choice. Use it when your app has an HTTP endpoint. Healthy if status is 200-399. <code>initialDelaySeconds</code> waits before first probe. <code>periodSeconds</code> sets interval. <code>failureThreshold</code> is consecutive failures before restart.</p>
      <Fragment slot="code">
```yaml
spec:
  containers:
    - name: app
      image: my-app:v1
      livenessProbe:
        httpGet:
          path: /health
          port: 8080
        initialDelaySeconds: 30
        periodSeconds: 10
        timeoutSeconds: 5
        failureThreshold: 3
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="pod-liveness-headers.yaml" />
    <Row last>
      <p slot="docs">HTTP probes can include custom headers for authentication or routing. Use <code>scheme: HTTPS</code> for TLS endpoints.</p>
      <Fragment slot="code">
```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
    scheme: HTTP
    httpHeaders:
      - name: X-Custom-Header
        value: probe
      - name: Authorization
        value: Bearer token
  initialDelaySeconds: 45
  periodSeconds: 30
```
      </Fragment>
    </Row>
  </tbody>
</table>

    <FileHeader filename="pod-liveness-tcp.yaml" />
    <Row last>
      <p slot="docs">TCP probe checks if the port accepts connections. Use for non-HTTP services (databases, Redis, gRPC without health checks). Limitation: it only confirms the port is open, not that the service is healthy. Prefer HTTP or exec when possible.</p>
      <Fragment slot="code">
```yaml
livenessProbe:
  tcpSocket:
    port: 5432
  initialDelaySeconds: 15
  periodSeconds: 20
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="pod-liveness-exec.yaml" />
    <Row last>
      <p slot="docs">Exec probe runs a command inside the container. Healthy if exit code is 0. Use for custom health logic (checking files, running CLI tools like <code>pg_isready</code>). More flexible but slower and uses more resources than HTTP/TCP.</p>
      <Fragment slot="code">
```yaml
livenessProbe:
  exec:
    command:
      - sh
      - -c
      - pg_isready -U postgres
  initialDelaySeconds: 30
  periodSeconds: 10
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">

    <FileHeader filename="pod-startup-probe.yaml" />
    <Row last>
      <p slot="docs">Startup probes replace liveness during container startup. Use for slow-starting apps instead of long initialDelaySeconds. Liveness probe only starts after startup probe succeeds. This example allows up to 5 minutes (30 × 10s) for startup.</p>
      <Fragment slot="code">
```yaml
spec:
  containers:
    - name: app
      startupProbe:
        httpGet:
          path: /health
          port: 8080
        failureThreshold: 30
        periodSeconds: 10
      livenessProbe:
        httpGet:
          path: /health
          port: 8080
        periodSeconds: 10
        failureThreshold: 3
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="pod-probe-params.yaml" />
    <Row last>
      <p slot="docs">Probe parameters: <code>failureThreshold</code> is consecutive failures before action. <code>successThreshold</code> is consecutive successes to recover (only for readiness). <code>timeoutSeconds</code> must be less than periodSeconds.</p>
      <Fragment slot="code">
```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 45
  periodSeconds: 30
  timeoutSeconds: 10
  failureThreshold: 3
  successThreshold: 1
```
      </Fragment>
    </Row>
  </tbody>
</table>

    <FileHeader filename="pod-liveness-best.yaml" />
    <Row last>
      <p slot="docs">Common mistakes: (1) Too aggressive settings cause restart loops. Increase timeoutSeconds for slow endpoints. (2) Checking dependencies like databases or external APIs. If the DB is down, restarting won't help and causes cascading failures. (3) Using liveness for apps that crash cleanly. Kubernetes already restarts crashed containers. Only use liveness for silent failures (deadlocks, hangs).</p>
      <Fragment slot="code">
```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  periodSeconds: 15
  timeoutSeconds: 5
  failureThreshold: 3
```
      </Fragment>
    </Row>
  </tbody>
</table>

    <TerminalHeader cmd="kubectl get pods" />
    <Row last terminal>
      <p slot="docs">Debug probe failures with events and logs. Container restarts increment the RESTARTS counter. Check probe endpoint directly with kubectl exec or port-forward.</p>
      <Fragment slot="code">
```bash
$ kubectl get pods
NAME     READY   STATUS    RESTARTS   AGE
my-app   1/1     Running   3          10m

$ kubectl describe pod my-app | grep -A5 "Liveness probe failed"
Warning  Unhealthy  2m  Liveness probe failed: HTTP probe failed
Warning  Unhealthy  1m  Liveness probe failed: HTTP probe failed

$ kubectl exec my-app -- curl -v localhost:8080/health
< HTTP/1.1 500 Internal Server Error

$ kubectl port-forward pod/my-app 8080:8080
$ curl localhost:8080/health
{"status": "unhealthy", "reason": "database connection failed"}
```
