<Intro>
  <p>A Pod is the atomic unit of scheduling in Kubernetes. It wraps one or more containers that share network and storage. Containers in a Pod communicate via <code>localhost</code> and share the same IP address, port range, and volumes.</p>
</Intro>

<table class="example-table">
  <tbody>
    <FileHeader filename="pod.yaml" />
    <Row>
      <p slot="docs">Pods use the core <code>v1</code> API. The <code>kind</code> tells Kubernetes what resource to create.</p>
      <Fragment slot="code">
```yaml
apiVersion: v1
kind: Pod
```
      </Fragment>
    </Row>
    <Row>
      <p slot="docs">The <code>name</code> uniquely identifies the Pod within its namespace. Labels enable selection and grouping.</p>
      <Fragment slot="code">
```yaml
metadata:
  name: my-app
  labels:
    app: my-app
```
      </Fragment>
    </Row>
    <Row>
      <p slot="docs">The <code>spec.containers</code> array defines the containers. Each needs a name and image.</p>
      <Fragment slot="code">
```yaml
spec:
  containers:
    - name: app
      image: nginx:alpine
```
      </Fragment>
    </Row>
    <Row last>
      <p slot="docs">Expose ports to make the container accessible. <code>containerPort</code> is informational but useful for documentation.</p>
      <Fragment slot="code">
```yaml
      ports:
        - containerPort: 80
```
      </Fragment>
    </Row>
  </tbody>
</table>

      <p slot="docs">Pod lifecycle states: <code>Pending</code> (waiting for scheduling or image pull), <code>Running</code> (at least one container running), <code>Succeeded</code> (all containers exited successfully), <code>Failed</code> (container exited with error).</p>
      <Fragment slot="code">
```bash
$ kubectl get pods -w
NAME     READY   STATUS    RESTARTS   AGE
my-app   0/1     Pending   0          0s
my-app   0/1     Pending   0          1s
my-app   0/1     ContainerCreating   0   2s
my-app   1/1     Running   0          5s
```
      </Fragment>
    </Row>

    <FileHeader filename="multi-container-pod.yaml" />
    <Row>
      <p slot="docs">Kubernetes creates a "pause" container that holds the network namespace. App containers join this namespace, sharing the same IP and using <code>localhost</code>.</p>
      <Fragment slot="code">
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-metrics
spec:
  containers:
    - name: web
      image: nginx
      ports:
        - containerPort: 80
```
      </Fragment>
    </Row>
    <Row last>
      <p slot="docs">Multi-container Pods are for tightly coupled workloads. Common patterns: sidecar (logging, proxies), ambassador (proxy to external services), adapter (transform output).</p>
      <Fragment slot="code">
```yaml
    - name: metrics
      image: prom/node-exporter
      ports:
        - containerPort: 9100
```
      </Fragment>
    </Row>
  </tbody>
</table>

<table class="example-table">
  <tbody>
    <FileHeader filename="sidecar-pod.yaml" />
    <Row>
      <p slot="docs">The sidecar pattern uses a shared volume. The main app writes logs, and the sidecar container ships them.</p>
      <Fragment slot="code">
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-sidecar
spec:
  containers:
    - name: app
      image: my-app:v1
      ports:
        - containerPort: 8080
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
```
      </Fragment>
    </Row>
    <Row>
      <p slot="docs">The sidecar reads from the same volume and forwards logs to your logging infrastructure.</p>
      <Fragment slot="code">
```yaml
    - name: log-shipper
      image: fluent-bit:latest
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
```
      </Fragment>
    </Row>
    <Row last>
      <p slot="docs"><code>emptyDir</code> creates a temporary directory that's shared between containers and deleted when the Pod terminates.</p>
      <Fragment slot="code">
```yaml
  volumes:
    - name: logs
      emptyDir: {}
```
      </Fragment>
    </Row>
  </tbody>

<table class="example-table">

    <FileHeader filename="pod-resources.yaml" />
    <Row>
      <p slot="docs">Resource requests and limits control CPU/memory allocation. Without limits, a Pod can consume all node resources.</p>
      <Fragment slot="code">
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-resources
spec:
  containers:
    - name: app
      image: my-app:v1
```
      </Fragment>
    </Row>
    <Row last>
      <p slot="docs"><code>requests</code> are guaranteed resources used for scheduling. <code>limits</code> are the maximum allowed. CPU is in millicores (100m = 0.1 cores).</p>
      <Fragment slot="code">
```yaml
      resources:
        requests:
          memory: "128Mi"
          cpu: "100m"
        limits:
          memory: "256Mi"
          cpu: "500m"
```
      </Fragment>
    </Row>
  </tbody>
</table>
